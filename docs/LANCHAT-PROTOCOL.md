# ThirdHub 局域网聊天协议（LANCHAT/1）

> 本文是**局域网聊天**（不经过任何服务器的那条路径）的单一事实来源。
> 与 [CHAT-PROTOCOL.md](CHAT-PROTOCOL.md) 的关系：**两套并存的通道，不是替代关系**。
>
> | | CHAT/1 | LANCHAT/1（本文） |
> |---|---|---|
> | 传输 | 后端 `/v1/chat/*` HTTP | 局域网 UDP 广播 + 点对点 HTTP |
> | 前提 | 有共同后端 | 同一 WiFi / 热点，**零服务器** |
> | 离线 | 服务端存储转发 | 交回后端（映射成 CHAT/1 会话） |
> | 加密 | 无（详见 CHAT/1 §7） | **X25519 + AES-256-GCM**（本文 §4） |
>
> 实现与本文一一对应，改一处必须同步另两处：
> - 纯逻辑：`flutter_app/lib/core/chat_logic.dart`（零 Flutter 依赖）
> - 加密：`flutter_app/lib/core/chat_crypto.dart`
> - 传输：`flutter_app/lib/core/chat_transfer.dart`
> - 自检：`flutter_app/tool/chat_proto_selfcheck.dart`

---

## 0. 三条底线

1. **零服务器可工作**。同 WiFi 下两台设备互见、互聊、互传文件，
   全程不经过任何服务器。**后端不是局域网聊天的前置条件。**
2. **发现 ≠ 信任**。UDP 广播只能证明"同一个网段里有这么个设备在喊"，
   不能证明它是谁。**加密身份由 §4 的密钥指纹独立确认**，不看广播里的名字。
3. **明文广播，密文私聊**。区域频道（一对多）刻意保持明文 + 显式标注；
   私聊（一对一）默认端到端加密。**绝不能让用户以为区域频道是加密的。**

## 1. 报文信封

沿用 `lanEncode` / `lanDecode` 的信封，版本升到 `2`：

```json
{ "app": "thirdhub", "v": 2, "t": "<类型>", ... }
```

`lanDecode` 的既有保证：非本应用（`app != 'thirdhub'`）、坏 JSON、缺 `t`
一律返回 `null`——**公网上什么 UDP 包都有，解析层绝不能崩**。这条在 v2 保持不变。

`v` 的处置：**不认识 `v` 的一律丢弃**（不猜测、不降级解析）。
v1 的 `hi` / `msg` 报文仍接受（兼容旧版设备在网），但回复时用 v2。

---

## 2. 报文类型

| `t` | 方向 | 说明 |
|---|---|---|
| `hi` | 广播 | 发现 + 公钥/能力声明。每 5 秒一次 |
| `msg` | 单播/广播 | 消息（文本/图片/文件引用） |
| `file` | 单播 | 文件传输要约（含下载地址与校验和） |
| `file_ack` | 单播 | 接收方确认（成功/拒绝/失败） |
| `typing` | 单播/广播 | 正在输入（**不进历史**） |
| `recall` | 单播/广播 | 撤回 |
| `bye` | 广播 | 主动下线（加速对端移除，不必等 45 秒超时） |

### 2.1 `hi` —— 发现 + 密钥交换

```json
{
  "app": "thirdhub", "v": 2, "t": "hi",
  "id": "dev-xxxx",           // 设备 id（持久化，非随机）
  "name": "客厅平板",
  "pk": "<base64 X25519 公钥 32B>",
  "fp": "<公钥指纹前 8 字节 hex>",   // 供用户肉眼核对
  "cap": ["text", "file", "voice"]  // 能力声明，接收方按需降级
}
```

- `pk` 由设备长期身份密钥对导出（§4.1），**不是每次广播临时生成**——
  指纹要稳定，否则用户每次核对都对不上。
- 收到 `hi` 时**回一个 `hi`**（加速双向发现），但如果源地址是广播且刚回过
  （< 3 秒），则不再回，避免两台设备互相回包形成风暴。

### 2.2 `msg` —— 消息

```json
{
  "app": "thirdhub", "v": 2, "t": "msg",
  "mid": "<消息 id>",          // 全局唯一，用于去重与撤回
  "id": "<发送设备 id>",
  "name": "客厅平板",
  "to": "dev-yyyy",            // 单播目标；广播时为 "*"
  "toAll": false,
  "kind": "text",              // text | image | file | voice | video | poke
  "ts": 1758432000000,
  // 以下二者必居其一：
  "text": "明文正文",           // enc == "none" 时
  "enc": "x25519-aesgcm",      // 或
  "ct": "<base64 密文>",
  "iv": "<base64 12B nonce>",
  "pk": "<base64 发送方一次性公钥>",
  // 附件（kind != text 时）
  "file": { "name": "a.pdf", "size": 12345, "mime": "application/pdf",
            "token": "<下载令牌>", "port": 45872, "sha256": "<hex>" }
}
```

**`mid` 是幂等键**：接收方按 `(id, mid)` 去重。局域网 UDP 会重复投递
（广播 + 单播可能同时到达），**没有 `mid` 就会看到两条一样的消息**。

### 2.3 `file` / `file_ack` —— 文件传输

见 §5。

### 2.4 `typing` / `recall` / `bye`

```json
{ "t": "typing", "id": "dev-xxxx", "to": "dev-yyyy", "on": true }
{ "t": "recall", "id": "dev-xxxx", "to": "*", "mid": "<被撤回的 mid>" }
{ "t": "bye",    "id": "dev-xxxx", "name": "客厅平板" }
```

- `typing` **不落盘、不进历史**，只在内存里存活 4 秒。
- `recall` 只撤回**自己发的**消息（接收方校验 `id` 与消息的 `from` 一致），
  且只在 5 分钟内有效。超时或非本人 → 静默忽略。

## 3. 去重与排序

| 规则 | 原因 |
|---|---|
| 按 `(from, mid)` 去重 | UDP 广播 + 单播双到达是常态 |
| 排序用 `ts`，同 `ts` 用 `mid` 字典序兜底 | 局域网内时钟通常同源，但**必须有确定性的兜底**，否则列表会随机跳动 |
| 单会话保留最近 500 条 | 本地存储不是归档 |
| `typing` 永不入库 | 它没有历史价值，入库会让"消息数"失真 |

## 4. 端到端加密（私聊默认开启）

### 4.1 身份密钥

- 每台设备首次启动生成一对 **X25519 长期密钥**，私钥存本机（`flutter_secure` 不可用时
  退化为 `SharedPreferences` 并**在 UI 明示"未受系统级保护"**）。
- 公钥随 `hi` 广播，**指纹**（公钥 SHA-256 前 8 字节 hex）展示给用户核对。

### 4.2 会话密钥

```
shared = X25519(my_priv, peer_pub)
salt   = SHA256("thirdhub-lanchat-v1" || sort(my_pub, peer_pub))
key    = HKDF-SHA256(ikm=shared, salt=salt, info="lanchat-msg", len=32)
```

- `sort(...)` 让双方算出**同一个** salt（谁先算都一样）。
- **每条消息用一次性临时密钥对**（`pk` 字段），做一次 X25519 与长期密钥混合：
  这样即使某条消息的临时私钥泄露，也换不到长期身份。
- 传输格式：`AES-256-GCM(key, iv=12B 随机, aad=mid||ts)`。
  把 `mid` 与 `ts` 放进 AAD，**篡改这两个字段会导致解密失败**。

### 4.3 降级规则

| 情况 | 行为 |
|---|---|
| 对端 `cap` 不含 `file` | 文件按钮置灰并说明原因，不静默失败 |
| 对端无 `pk`（旧版设备） | **明文发送**，但消息气泡上标"未加密"，不假装加密 |
| 解密失败 | 显示"无法解密（密钥可能已变化）+ 重新配对按钮"，绝不显示乱码 |

> **红线**：绝不把"解密失败"渲染成一段看起来像正文的乱码。用户会以为对方发了怪话。

### 4.4 区域频道的定位

区域频道（`toAll: true`）**刻意不加密**：一对多场景下的群密钥分发是另一个大问题，
本轮不做，也**不假装做了**。UI 上常驻一行提示：

> 区域频道为局域网广播，同网段设备均可看到，未加密。

## 5. 文件传输

### 5.1 流程

```
发送方                                        接收方
  │  起临时 HttpServer（随机端口，仅绑定内网）
  │  ──── file 要约（name/size/mime/token/port/sha256）────►
  │                                              │ 校验 token，弹确认
  │  ◄──── file_ack { ok: true } ────────────────┤
  │  ◄──── GET /dl/<token> ──────────────────────┤  流式下载
  │  ──── 200 + 字节流 ─────────────────────────►│ 边下边算 SHA-256
  │                                              │ 校验和比对 → 落盘
  │  ◄──── file_ack { ok: true, saved: "..." }───┤
  │  关闭临时服务（无流量 90 秒后自动关）
```

### 5.2 约束

| 约束 | 值 | 原因 |
|---|---|---|
| 单文件上限 | 2 GB | 超过走"文件互传"模块，不是聊天 |
| 临时服务绑定地址 | 内网网卡，**不是 0.0.0.0** | 不把文件暴露给公网 |
| 令牌 | 32 字节随机，一次性 | URL 猜不到；用过即失效 |
| 校验 | 整包 SHA-256 | 局域网也会因路由器丢包而损坏 |
| 空闲自动关闭 | 90 秒 | 不留常驻端口 |

### 5.3 接收方拒绝

`file_ack { ok: false, reason: "declined" | "too_large" | "busy" }`。
发送方**必须**给用户明确反馈，不能"发了没反应"（STYLE_GUIDE 第 2 条：错误三段式）。

## 6. 离线消息（交回后端）

局域网聊天的"离线"只有一种含义：**对方此刻不在同一个网段**。

处置顺序：

1. 单播 `msg` 发出后 **8 秒内**未收到对端的 `msg` 回执（`t: "ack"` 内嵌于
   `msg` 的 `ackOf` 字段）→ 判定为"可能不在线"。
2. 此时**不再无限重试广播**（会污染网络）。改为把该消息写入 CHAT/1 的发件箱
   （`chat_outbox`），会话 id 用 `lan:<peerId>`。
3. 对端下次上线（连上共同后端）时，走 CHAT/1 §5 的 `flush()` 收走。

**这条路径的代价必须对用户可见**：气泡上从"已送达"变为"待同步"，
点击可看到原因（`现象/原因/怎么办` 三段）。

## 7. 已知边界

- **没有群密钥**。区域频道明文，见 §4.4。
- **没有离线留言加密**。走 CHAT/1 后端的消息**不带端到端加密**（CHAT/1 §7 同款边界）。
  真要私密请用私聊直连，或自行在正文层加密。
- **没有跨网段**。UDP 广播不出路由器；跨网段需要 IPv6/内网穿透，本轮不做。
- **没有密钥轮换**。长期身份密钥一旦生成即固定；换机即换身份，
  指纹变化时必须要求用户重新核对。

## 8. 自检

```bash
dart run tool/chat_proto_selfcheck.dart
```

覆盖：信封兼容（v1 旧报文仍可解析）/ `mid` 去重 / 排序确定性 /
AES-GCM 往返 + **篡改 AAD 必失败** / 指纹稳定性 / 降级到明文时 `enc` 字段正确 /
文件令牌一次性 / 超长正文截断。
