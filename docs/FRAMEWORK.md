# ThirdHub 统一框架（唯一准绳）

> 本文取代此前所有 `ARCHITECTURE.md` / `ARCHITECTURE-V2.md` / 「v4 架构总纲」。
> 以后讨论架构，只认这一份。版本号只代表发布序号，**不再作为体系名**——
> 不存在「v2 版」「v4 版」，只有同一个 ThirdHub 的不同发布。

---

## 1. 命名与版本

| 概念 | 规则 |
|---|---|
| 产品名 | **ThirdHub**（一个产品，一条演进线） |
| 版本号 | 4.81.x 这类只是**发布序号**，用于升级判定；不代表架构换代 |
| 文档 | 不再出现「v2 架构」「v4 架构」；需要指代历史时写「改造前 / 改造后」 |
| 仓库 | 保留历史仓库名（`ThirdHub-v2` 等），但它们是**同一产品的不同部件**，不是不同版本 |

历史脉络（一条线，不是并列版本）：

```
OmniHub（初代安卓）
   └─ ThirdHub-Android（Kotlin 壳，已退役）
        └─ ThirdHub-Flutter ──► ThirdHub-v2（当前主前端 + 家庭后端 + 对外文档）
网页端 ThirdHub（CF Pages）──► 与 App 同契约的另一前端
引擎 ReadingEngine ──► ThirdHub-Engine-{Novel,Comic,Music,Video}
站点 ThirdHub-Portal / ThirdHub-Admin / ThirdHub-Update
```

## 2. 唯一权威划分：**两面 + 两端**

这是本文最重要的一条。以前把「网页端 / 安卓端 / Windows 端」并列成三端，
于是每加一个平台就要重写一遍适配逻辑，越写越乱。

**真正的第一性划分是前后端两面；「移动端 / 桌面端」只是前端这一面的两种形态。**

```
               ┌──────────── 前端（呈现面）────────────┐
   移动端形态  │  Android · iOS · 鸿蒙 · 微信小程序 · 网页/PWA │
   桌面端形态  │  Windows · macOS · Linux · 容器内浏览器        │
               └───────────────────┬───────────────────┘
                                   │ THP 契约（REST/WS/SSE + 统一 IR）
               ┌───────────────────▼───────────────────┐
               │        后端（能力面，可缺席）           │
               │  家庭后端(NAS/Docker) · 本机进程 · 云端兜底 │
               └───────────────────┬───────────────────┘
                                   │ 引擎契约
               ┌───────────────────▼───────────────────┐
               │  内容来源：端上直连公网 / 引擎插件 / 用户媒体库 │
               └────────────────────────────────────────┘
```

### 归属判定只问两个问题

1. **它在哪里跑？** → 决定「面」：显示与交互在前端，规则解析与存储在后端。
2. **它怎么被操作？** → 决定「端形态」：触屏竖屏＝移动端形态；键鼠多窗口＝桌面端形态。

> 所以「电脑上的网页版」属于**移动端形态**（浏览器/PWA，触屏或触摸板优先），
> 而「NAS 容器里跑的同一份网页」属于**桌面端形态**（键鼠、多窗口、常驻）。
> 同一份前端代码，形态由运行环境决定，不由操作系统名字决定。

### 关键结论

- **前端只有一份能力事实**：能显示、能播放、能输入。它不知道内容从哪来。
- **后端可以完全没有**：端上直连层负责兜住「后端不存在」的场景（见 §6）。
- **平台差异只允许出现在两处**：壳层（权限/通知/文件选择/窗口管理）和
  输入适配（手势 vs 快捷键）。**不允许**在业务代码里写 `if (Platform.isAndroid)`。

## 3. 前端矩阵

| 形态 | 载体 | 代码来源 | 壳层职责 | 状态 |
|---|---|---|---|---|
| 移动端 | Android | `flutter_app/` 同一份 | 权限、前台服务、通知、安装包 | ✅ 主力 |
| 移动端 | iOS | 同上 | 后台音频、文件导入、无第三方影视采集 | 🟡 有配置无发布链 |
| 移动端 | 鸿蒙 | 同上（Flutter 鸿蒙分支）或 ArkTS 壳 | 分布式流转、卡片 | ⬜ 未做 |
| 移动端 | 微信小程序 | 独立轻前端（Taro/原生） | 登录、分享、扫码 | ⬜ 未做 |
| 移动端 | 网页 / PWA | `ThirdHub` 仓（CF Pages） | 无需安装、可加桌面 | 🟡 线上版本落后 |
| 桌面端 | Windows | `flutter_app/` 同一份 | 托盘、自启、多窗口、文件关联 | 🟡 有 CI 矩阵无平台目录 |
| 桌面端 | macOS | 同上 | 菜单栏、沙盒授权 | 🟡 同上 |
| 桌面端 | Linux / 容器 | 同上 + Docker 镜像 | 无头运行、反代、数据卷 | 🟡 Docker 用于后端为主 |

## 4. 后端矩阵

| 部署形态 | 位置 | 用途 | 状态 |
|---|---|---|---|
| 家庭后端 | NAS 容器（`:9527`） | 能力路由、存储、同步、代理签名 | ✅ 线上 0.8.8 |
| 本机进程 | 用户电脑 | 无 NAS 时的等价能力 | 🟡 脚本可用，无安装器 |
| 端内嵌 | 安卓 App 内 | 后端起不来时的最小能力 | ⬜ 未做 |
| 云端兜底 | 托管服务 | 无家庭后端时的公共能力（限流） | ⬜ 未做 |

**后端永不承担：** 内容版权判定、用户数据落地（除缓存与用户自有库）、
前端渲染决策。

## 5. 契约层（唯一事实来源）

| 契约 | 作用 | 位置 |
|---|---|---|
| **THP** | 前后端之间：统一信封、能力协商（caps）、分页游标、错误码、事件订阅、blob 分块 | `docs/THP.md` |
| **IR** | 内容归一：`novel-ir` / `comic-ir` / `video-ir` / `music-ir`，前端只认 IR | `docs/THP.md` + `contracts/` |
| **PH/1** | 端到端：设备发现（UDP/mDNS）、跨端互调、权限与令牌 | `docs/AGENT-PROTOCOL.md` |
| **PLUGIN-SDK** | 第三方引擎接入，官方引擎零改动 | `docs/PLUGIN-SDK.md` |
| **AGENT-PROTOCOL** | App 内 AI 控制总线（真机自动化测试） | `docs/AGENT-PROTOCOL.md` |

铁律：**新增能力只能扩展契约，不得修改已有字段语义**。前端遇到未知字段必须忽略而不是崩溃。

## 6. 内容来源三层（后端可缺席的关键）

| 层 | 含义 | 例子 | 后端依赖 |
|---|---|---|---|
| **L-A 端上直连** | 前端直接调公网正规接口，无后端、无 token | MangaDex、Audius、iTunes 播客、radio-browser、PeerTube、Gutenberg AU、维基文库、今日诗词 | ❌ 零依赖 |
| **L-B 家庭后端** | 后端按 caps 路由到内置引擎或用户媒体库 | drpy 影视、Venera 漫画、MusicFree 音源、Legado 书源、NAS 影视/音乐库 | ✅ 必需 |
| **L-C 引擎插件** | 局域网内独立跑的官方原版（零改动） | Legado 官方版、Komga、Audiobookshelf | 经后端编排 |

设计意图：**L-A 保证"软件本身永远有东西可看"**，L-B/L-C 才是"内容全"。
任何新板块上线时，必须同时回答：后端不在时它剩下什么？（可以是"什么都没有，但要说清为什么"）

## 7. 降级矩阵

| 故障 | 行为 | 用户看到 |
|---|---|---|
| 家庭后端离线 | 自动切 L-A 端上直连 | 顶部提示「后端未连接，正在用开放内容」+ 一键去连 |
| 某引擎离线 | 自动摘除该来源，其余照常 | 结果页标注来源缺失，不报错 |
| 公网源不可达 | 标记该源灰色 + 重试按钮 | 「这个源现在不通」，**不**表现成"没内容" |
| 弱网/超时 | 18 秒上限 + 可取消 | 进度 + 「停止」按钮，绝不无限转圈 |
| 无网络 | 本地库/已下载内容仍可播 | 明确横幅，不做假成功 |
| 权限缺失 | 请求权限并说明用途 | 拒绝后给替代路径（浏览器下载等） |

## 9. 复刻成熟度（对标大厂的验收尺）

「像大厂」不是观感，是可判定的等级。每个模块都要在 `docs/BENCHMARK.md` 里标一个等级：

| 级 | 名称 | 判定标准 |
|---|---|---|
| **R0** | 占位 | 有入口，进去是说明页或空列表 |
| **R1** | 可用 | 真实数据能跑通主流程（搜到→打开→播/读） |
| **R2** | 对齐 | 关键交互与大厂一致：手势、快捷键、空态、错误态、继续观看位 |
| **R3** | 健壮 | 弱网/离线/权限/超大列表/异常输入都有确定行为；多端一致 |
| **R4** | 精致 | 无障碍（读屏/对比度/大字号）、动效克制、首屏性能达标、全语言无漏译 |

**发布纪律：** 更新日志只允许把 R≥2 的模块写成"新能力"；R0/R1 只能写"继续完善"。
这条用来防止「宣称做了、实际只是有个入口」再次发生。

## 12. 当前已知架构债务（按优先级）

1. **网页端部署链路断裂**：CF Pages 无 Git 集成，三方版本漂移（线上 3.43.10 / 仓库 3.43.11 / NAS 3.43.9）。
2. **桌面端无平台目录**：CI 有三平台矩阵，但缺 `windows/` `macos/` `linux/`，构建必失败。
3. **`main.dart` 18.5k 行单文件**：61 个模块与全部页面挤在一处，任何改动都要全量解析。
4. **255 处 `catch (_) {}`**：异常被静默吞掉，是"点了没反应"的主要来源。
5. **阅读进度多端覆盖无冲突合并**：后写赢，跨端同时读会丢进度。
